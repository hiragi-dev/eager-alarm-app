# 既知の問題

## PWAを更新するとMQTT設定と停止方法が消える

### 症状

**Cloudflare Workers にデプロイした本番サイト**
（https://eager-alarm-app.flukekit0316.workers.dev ）をPWAとして使っていると、
アプリを更新したあとに開いたときに、MQTT接続設定（ブローカーURL・ユーザー名・パスワード・
デバイスID）と、登録済みの停止方法（位置情報ベース）が **どちらも空になっている**。

毎回手で入力し直す必要があり、停止方法を作り直すとアラーム側の割り当ても失われる。
ローカルの開発サーバーではなく、デプロイ済みサイトで起きている点が本質です。

### 分かっていること

**アプリのコード側（確認済み）**

- どちらの設定もブラウザの localStorage にのみ保存している。キーは MQTT設定が
  `mqtt-demo-settings`（`src/lib/mqtt.ts`）、停止方法が `STOP_METHOD_STORAGE_KEY`
  （`src/lib/stopMethod.ts`）で、両者は完全に独立している
- 保存はユーザーが値を変更したその場で行っている（`src/contexts/MqttProvider.tsx` の
  `updateSetting`、`src/contexts/StopMethodProvider.tsx` の `persist`）。
  「保存ボタンの押し忘れ」で消える作りではない
- **アプリ側に localStorage を削除するコードは存在しない**（`removeItem` / `clear` の
  呼び出しはゼロ）
- Service Worker（`public/sw.js`）はキャッシュを一切持たず、`install` で `skipWaiting()`、
  `activate` で `clients.claim()` を呼ぶだけ。Service Worker の更新が localStorage を
  消すことはない
- `navigator.storage.persist()`（ストレージの永続化要求）は呼んでいない

**デプロイ先の実測（2026-07-28 時点、修正前）**

- `/`（HTML）のレスポンスヘッダーは `cache-control: s-maxage=31536000` のみ。
  ブラウザ向けの `max-age` がなく、`ETag` も `Last-Modified` も付いていない。
  **検証材料が無いため、ブラウザは古いHTMLの新しさを確かめる術がない**
- `/sw.js` と `/_next/static/*` は `cache-control: public, max-age=0, must-revalidate` に
  `ETag` 付き。これは Workers Static Assets 側の既定値で、`next.config.ts` の指定ではない。
  つまり **静的アセットは元から毎回再検証されており、検証材料が無かったのはHTMLだけ**
- `Clear-Site-Data` ヘッダーは送出していない

**ここから言えること**

オリジンは workers.dev で固定なので、「アクセスするURLが変わって別の保存領域を見ている」
という説明は成り立ちません。そして独立した2つのProviderの保存内容が同時に失われている以上、
**そのオリジンのlocalStorageが領域ごと破棄されている**と考えるのが自然です。
アプリのコードが消しているわけではありません。

### 原因の候補

確度の高い順。いずれも実機では未確認です。

**1. 更新を反映させるための操作そのものがストレージを消している（最有力）**

このアプリのService Workerはオフラインキャッシュを持たないため、更新の反映は
ブラウザのHTTPキャッシュ任せです。ところが実測のとおり `/` のHTMLには
ブラウザ向けの `max-age` も `ETag` も `Last-Modified` もありません。検証材料が無いため、
ブラウザが古いHTMLを保持したままになると「デプロイしたのに新しくならない」状態が起こり得ます。

それを解消するために **「Webサイトデータを消去」やPWAの再インストール**を行えば、
localStorage も一緒に消えます。この場合、設定を消しているのは更新そのものではなく
**更新を反映させるための操作**です。「更新のたびに消える」という規則性とよく合致します。

**2. ブラウザによるストレージの追い出し（eviction）**

iOS Safari（ITP）は、一定期間ユーザー操作のないサイトのスクリプト書き込みストレージを
削除します。本アプリは `navigator.storage.persist()` による永続化要求をしていないため
対象になり得ます。ホーム画面に追加したWebアプリがこの対象になるかはOSバージョンで
挙動が異なるとされており、確認が必要です。

なお `workers.dev` は Public Suffix List に載っているため、
`eager-alarm-app.flukekit0316.workers.dev` は独立した1サイトとして扱われます。
他サイトの利用実績はこのサイトの保持判断には効きません。

**3. PWAの入れ直しによるストレージ区画の破棄**

iOSではホーム画面のWebアプリと通常のSafariタブでストレージ区画が分かれることがあり、
アイコンを削除して再追加すると、そのアプリのストレージは破棄されます。
「更新」の手順にアイコンの削除・再追加が含まれるなら、これが直接の原因です。

### 対応状況（2026-07-28）

短期対策のうち3点を実装済みです。**いずれも症状が直ったことの確認は取れていません**。
原因が候補1でなかった場合、消失は続きます。

- **HTMLに明示的なキャッシュ指定を追加**（`next.config.ts`）。
  ローカルプレビューで `/` が `cache-control: public, max-age=0, must-revalidate` と
  `ETag` を返すことを確認済み。ハッシュ付きの `/_next/static/*` の扱いは変えていない
- **ストレージの永続化要求を追加**（`src/components/StoragePersistence.tsx`）。
  `navigator.storage.persist()` を起動時に一度呼ぶ。未対応ブラウザでは何もしない
- **保存値を読めなかったときの書き戻しを停止**（`src/contexts/MqttProvider.tsx`。
  下記「副次的に見つかったコード上の弱点」への対応）

残っているのは切り分け手順の実施と、中期の対策（設定のエクスポート/インポート、
消失時の明示）です。

### 副次的に見つかったコード上の弱点

主原因ではありませんが（停止方法も同時に消えている事実と整合しないため）、
`src/contexts/MqttProvider.tsx` の初回マウント処理には壊れやすい経路があります。

保存値の `JSON.parse` に失敗すると `saved` を `null` に倒し、その直後に
`{ ...(saved ?? {}), deviceId }` を localStorage へ書き戻します。つまり
**保存値が壊れていた場合、ブローカーURL・ユーザー名・パスワードを自ら消してしまいます**。
書き込みが中断されて半端な値が残ったケースなどで、復旧不能な上書きが起こり得ます。

対応済み: 読み取りに失敗した場合（`JSON.parse` の失敗、値がオブジェクトでない場合を含む）は
書き戻さないようにしました。「保存が無い（初回起動）」との区別が必要なため、
`saved` が `null` かどうかではなく、読み取りに失敗したかを別途持って判定しています。

### 切り分け手順

1. まず「更新」が具体的に何を指すのかを確定させる（再デプロイ後に開き直すだけなのか、
   アイコンを入れ直しているのか、サイトデータを消去しているのか）。
   候補1〜3のどれに当たるかがこれで決まる
2. 消える前に、リモートデバッグ（iOSはMacのSafari Web Inspector、Androidは
   `chrome://inspect`）で `localStorage.getItem("mqtt-demo-settings")` に値があることを確認する
3. 更新後に同じ確認を行う。`null` になっていればストレージの破棄、値が残っているのに
   画面が空なら復元側の不具合であり、調べる場所が変わる
4. サイトデータの消去やアプリの入れ直しを **一切せずに** 更新した場合にも再現するかを見る。
   再現しなければ候補1で確定

### 対策案

**短期** — いずれも実装済み（「対応状況」参照）

**中期**

- 設定のエクスポート／インポート（JSONの貼り付け、またはQRコード）を用意し、消えても
  数秒で復旧できるようにする。デバイスIDは既にQRペアリングを見据えた一意IDになっている
- 保存値が見つからない場合に「設定が見つかりません。再入力してください」と明示する。
  現状は空欄で立ち上がるだけで、初回起動なのか消失なのかユーザーが区別できない
- 設定の保管場所をブラウザ外（edge側またはサーバー側）に持たせる案。ただしMQTT認証情報を
  どこに置くかは別途設計が必要

### まだ確認していないこと

- 実機での再現確認、およびリモートデバッグでの localStorage の実際の中身
- 「更新」の具体的な操作内容（切り分け手順1）
- 古いHTMLが実際にキャッシュされたままになっていたのか（修正前の挙動は確認できていない）
- 今回の修正で症状が止まるかどうか。修正はデプロイして初めて効くため、
  次のデプロイ以降の更新で消失が起きなくなるかを見る必要がある
